# Инструкции для AI-агента: Backend

## 1. Контекст проекта

Мы разрабатываем backend для тестового приложения AI Image Generator.

Пользователь отправляет текстовый prompt и параметры изображения. Сервер имитирует асинхронную генерацию: ждёт несколько секунд и возвращает заранее подготовленный PNG-файл.

Реальной генерации изображений нет. Внешние API, API-ключи и доступ в интернет не требуются.

Главная цель — простая, понятная и проверяемая реализация, соответствующая требованиям тестового задания.

Перед внесением изменений изучи:
- `docs/requirements.md` — функциональные и нефункциональные требования.
- `docs/architecture.md` — архитектура и принятые технические решения.
- API-контракт, зафиксированный в проектной документации.

Если инструкция противоречит этим документам, не выбирай решение самостоятельно: сообщи о противоречии.

## 2. Технологический стек

Обязательный стек:
- Python.
- FastAPI.
- SQLite.
- Docker Compose.
- pytest для тестирования.

Не добавляй Redis, Celery, брокеры сообщений, отдельные worker-процессы и другие инфраструктурные компоненты.

Backend должен запускаться одной командой:

`docker compose up --build`

Сервер должен работать без регистрации во внешних сервисах, API-ключей и доступа в интернет.

## 3. Архитектурные принципы

- Один backend-процесс: HTTP API и работа с SQLite.
- Асинхронность генерации реализуется через `ready_at` и polling.
- Отдельного фонового worker нет.
- Состояние генераций и подписок хранится в SQLite.
- PNG-файлы-источники хранятся в репозитории.
- Готовые изображения копируются в постоянный каталог данных.
- Не создавай дополнительные архитектурные слои без конкретной необходимости.
- Не добавляй абстракции «на будущее».
- Код должен оставаться простым для чтения и проверки.

## 4. Идентификация пользователя

Каждый API-запрос должен содержать заголовок:

`X-User-Id: <UUID>`

Правила:
- UUID используется для идентификации пользователя, но не является механизмом авторизации.
- Отсутствующий заголовок возвращает `400 USER_ID_REQUIRED`.
- Некорректный UUID возвращает `400 INVALID_USER_ID`.
- При первом запросе с корректным UUID сервер создаёт пользователя со статусом `free`.
- Все генерации и подписки изолированы по `userId`.
- Нельзя возвращать пользователю данные другого пользователя.

Клиентское состояние `unknown` не существует на стороне API.

## 5. Подписки

Допустимые серверные статусы:
- `free`
- `premium`

Новый пользователь всегда получает `free`.

Premium-опции:
- `anime`
- `cinematic`
- `hd` (quality)

При попытке использовать Premium-опцию пользователем со статусом `free` сервер возвращает:

- HTTP `403`
- Код `PREMIUM_REQUIRED`

Проверка подписки выполняется до создания записи генерации.

### Покупка

`POST /api/subscription/purchase`

- Переводит пользователя в `premium`.
- Не требует тела запроса.
- Повторный вызов идемпотентен.
- Повторная покупка не создаёт дубликатов и не вызывает ошибку.
- API не предоставляет способа вернуть пользователя в `free`.

## 6. Генерации

### Допустимые параметры

Styles:
- `photorealistic`
- `digital-art`
- `anime`
- `cinematic`

Aspect ratios:
- `1:1`
- `2:3`
- `16:9`

Quality:
- `standard`
- `hd`

Неизвестные значения возвращают `400 INVALID_REQUEST`.

Пустой prompt или prompt, состоящий только из пробелов, возвращает `400 INVALID_REQUEST`.

### Создание генерации

`POST /api/generations`

Порядок обработки:
1. Проверить `X-User-Id`.
2. Проверить тело запроса и все параметры.
3. Проверить Premium-доступ.
4. Только после успешных проверок создать запись генерации.

Успешный ответ:
- HTTP `201`
- UUID генерации.
- Статус `pending`.

При ошибке валидации или Premium-доступа запись генерации не создаётся.

### Статусы

Допустимые статусы:
- `pending`
- `processing`
- `completed`
- `failed`

`pending` возвращается при создании генерации.

При последующих запросах:
- До наступления `ready_at` возвращается `processing`.
- После наступления `ready_at` генерация переходит в конечное состояние.

### Асинхронная механика

- При создании генерации сервер записывает `ready_at` примерно на 3 секунды вперёд.
- Первый GET до наступления срока переводит `pending` в `processing`.
- Повторные GET до наступления срока возвращают `processing`.
- После наступления срока генерация завершается.
- Отдельного фонового процесса нет.

Завершение должно быть идемпотентным: повторные GET после завершения возвращают тот же результат, не копируют файл заново и не меняют статус.

После перезапуска сервера генерация должна корректно завершаться по сохранённому `ready_at`.

## 7. Намеренная ошибка генерации

Специальный prompt:

`trigger-error`

Он проходит обычную валидацию и создаёт запись генерации.

После наступления `ready_at` генерация завершается со статусом `failed`.

Ответ:
- HTTP `200`
- `status: failed`
- `error.code: GENERATION_FAILED`

HTTP `500` для этого сценария использовать запрещено.

Сравнение prompt с `trigger-error` точное. Пробелы вокруг строки не должны превращать другой prompt в специальный.

## 8. Изображения

PNG-файлы-заглушки лежат в `backend/assets/`.

При успешном завершении:
1. Сервер выбирает PNG по стилю.
2. Копирует его в `backend/data/images/{generation_id}.png`.
3. Сохраняет ссылку на файл в SQLite.
4. Возвращает `completed` и `imageUrl`.

Путь к результату:

`/static/generated/{generation_id}.png`

Файл должен переживать перезапуск контейнера благодаря постоянному каталогу данных.

Endpoint выдачи изображения:
- Возвращает байты PNG.
- Проверяет `X-User-Id`.
- Проверяет принадлежность генерации пользователю.
- Не отдаёт изображение, если генерация ещё не завершена.
- Для чужой или отсутствующей генерации возвращает `404 NOT_FOUND`.

Content-Type успешного ответа: `image/png`.

## 9. API

Реализуй следующие endpoints:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/subscription` | Получить статус подписки |
| POST | `/api/subscription/purchase` | Mock-покупка Premium |
| POST | `/api/generations` | Создать генерацию |
| GET | `/api/generations/{id}` | Получить статус генерации |
| GET | `/api/generations` | Получить серверную историю |
| GET | `/static/generated/{id}.png` | Скачать результат |

Все JSON-ответы и запросы используют `application/json`, кроме выдачи изображения.

Все тексты ошибок API — на английском.

### Формат HTTP-ошибок

Единый формат:

```json
{
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable message"
  }
}
```

Коды:

| HTTP | Код | Причина |
|---|---|---|
| 400 | `USER_ID_REQUIRED` | Нет заголовка |
| 400 | `INVALID_USER_ID` | Некорректный UUID |
| 400 | `INVALID_REQUEST` | Некорректное тело или параметры |
| 403 | `PREMIUM_REQUIRED` | Нет Premium-подписки |
| 404 | `NOT_FOUND` | Генерация отсутствует или принадлежит другому пользователю |
| 500 | `INTERNAL_ERROR` | Непредвиденная ошибка сервера |

Не используй HTTP `500` для бизнес-ошибки генерации.

## 10. Серверная история

`GET /api/generations`

Возвращает все генерации текущего пользователя в порядке от новых к старым.

Каждая запись содержит:
- `id`
- `status`
- `prompt`
- `options`
- `imageUrl`
- `error`
- `createdAt`

Статусы в истории:
- `processing`
- `completed`
- `failed`

Для незавершённых генераций `imageUrl` и `error` равны `null`.

Для неуспешных генераций `imageUrl` равен `null`, а `error` содержит `GENERATION_FAILED`.

Пустая история возвращает:

```json
{
  "generations": []
}
```

Клиентское приложение использует локальную историю. Серверная история хранится независимо и не синхронизируется с клиентом.

## 11. Хранение данных

SQLite должна хранить:
- пользователей;
- статусы подписок;
- генерации;
- параметры генераций;
- статусы;
- `ready_at`;
- ссылки на изображения;
- коды ошибок;
- время создания.

Данные должны быть изолированы по `userId`.

Файловая структура:

```text
backend/
  app/
  assets/
  data/
    images/
  tests/
```

`backend/data/` должен сохраняться между перезапусками контейнера.

Схема базы создаётся при старте приложения. Отдельная сложная система миграций не нужна.

## 12. Тестирование

Используй pytest.

Обязательные сценарии:

1. Новый пользователь получает `free`.
2. Получение подписки возвращает корректный статус.
3. Покупка переводит пользователя в `premium`.
4. Повторная покупка идемпотентна.
5. Free-пользователь может создать бесплатную генерацию.
6. Free-пользователь не может создать Premium-генерацию.
7. При `403 PREMIUM_REQUIRED` запись генерации не создаётся.
8. Premium-пользователь может использовать Premium-опции.
9. Пустой prompt возвращает `400`.
10. Неизвестные значения параметров возвращают `400`.
11. `trigger-error` завершается статусом `failed` и HTTP `200`.
12. Успешная генерация возвращает `completed` и доступный PNG.
13. Пользователь не может получить чужую генерацию.
14. Пользователь не может скачать чужое изображение.
15. История возвращает только генерации текущего пользователя.
16. Завершённая генерация сохраняет результат после повторного GET.
17. Незавершённая генерация корректно завершается после рестарта приложения при наступлении `ready_at`.

Тесты не должны зависеть от реального ожидания в несколько секунд. Используй управляемое время или явно задаваемый `ready_at`.

## 13. Правила работы AI-агента

- Перед реализацией изучи существующий код и документацию.
- Не переписывай уже работающий код без необходимости.
- Не меняй API-контракт без явного согласования.
- Не добавляй новые endpoints, поля ответа или бизнес-сценарии без необходимости.
- Не добавляй зависимости, если задачу можно решить стандартными средствами или уже установленными библиотеками.
- Не дублируй бизнес-логику между endpoints.
- Не скрывай ошибки широкими `except Exception` без логирования и корректной обработки.
- Не возвращай внутренние traceback или детали инфраструктуры клиенту.
- Не используй глобальное состояние в памяти для данных, которые должны переживать рестарт.
- Не усложняй проект дополнительными слоями, паттернами и абстракциями без практической причины.
- Не изменяй файлы frontend и общую документацию, если задача касается только backend.
- После каждого законченного этапа запускай соответствующие тесты.
- Если обнаружено противоречие в требованиях или контракте, сначала сообщи о нём, а не принимай самостоятельное продуктовое решение.

## 14. Критерии готовности backend

Backend считается готовым, когда:

- Запускается одной командой.
- Не требует внешнего интернета и API-ключей.
- Все endpoints соответствуют API-контракту.
- Все обязательные тесты проходят.
- Данные переживают перезапуск контейнера.
- Premium-проверка выполняется на сервере.
- Изображения доступны только владельцу генерации.
- Ошибки возвращаются в согласованном формате.
- README содержит инструкции запуска и проверки API.
