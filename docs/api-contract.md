# API contract

Источник: `docs/requirements.md`, `docs/architecture.md` и подтверждение контракта. Клиент и сервер используют только эти вызовы.

## Подтверждённые решения

- `POST /api/generations` возвращает `201`: ресурс создан.
- Статус подписки в JSON — строчные `free` и `premium`.
- `pending` возвращает только создание. Дальнейшие `GET` возвращают `processing` или конечный статус.
- Файл картинки скачивается отдельным `GET` по относительному `imageUrl`. Запрос проверяет `X-User-Id`.
- Первый `GET` после `ready_at` завершает генерацию. Повторные `GET` возвращают тот же результат, не копируют PNG заново и не меняют статус.
- Повторный `GET` после `failed` всегда возвращает тот же `failed` и тот же код ошибки.
- `imageUrl` — относительный путь. Клиент разрешает его относительно baseUrl.

## Общие правила

Каждый запрос несёт заголовок `X-User-Id`. Это анонимная идентификация, не авторизация. Значение — UUID. Сервер ищет пользователя по этому значению. Если пользователя ещё нет, создаёт его со статусом `free`.

Клиентское `unknown` в API не существует: сервер его не принимает и не возвращает.

Тела запросов и ответов — `application/json`, кроме файла картинки. Тексты ошибок — на английском.

Ошибки HTTP имеют один формат:

```json
{
  "error": {
    "code": "ERROR_CODE",
    "message": "What the client can show"
  }
}
```

| Код | HTTP | Когда |
| --- | --- | --- |
| `USER_ID_REQUIRED` | 400 | Заголовка нет |
| `INVALID_USER_ID` | 400 | Значение не UUID |
| `INVALID_REQUEST` | 400 | Тело не разбирается, поле пропущено, prompt пустой или значение опции неизвестно |
| `PREMIUM_REQUIRED` | 403 | В запросе есть Premium-опция, а пользователь Free |
| `NOT_FOUND` | 404 | Генерация не найдена или принадлежит другому `userId` |
| `INTERNAL_ERROR` | 500 | Непредвиденный сбой сервера |

`500` не используется для `trigger-error`. Бизнес-ошибка генерации приходит как `200` и статус `failed`.

Для `POST /api/generations` сервер действует в таком порядке:

1. Проверяет `X-User-Id`.
2. Проверяет тело и допустимые значения. Пустой prompt и неизвестная опция дают `400`, запись не создаётся.
3. Если `style` равен `anime` или `cinematic`, либо `quality` равен `hd`, а подписка `free`, возвращает `403` до создания записи. `trigger-error` эту проверку не обходит.
4. Только после этого создаёт генерацию.

Premium-значения — `anime`, `cinematic`, `hd`. Соотношения сторон `1:1`, `2:3`, `16:9` бесплатны всегда.

## GET /api/subscription

Возвращает серверный статус подписки. Клиент вызывает его при запуске, из настроек и перед Premium-опцией, пока кэш ещё `unknown`.

Заголовки: `X-User-Id`. Тела нет.

`200`

```json
{
  "status": "free"
}
```

`status` — `free` или `premium`. Для нового пользователя ответ `free`.

Ошибки: `400` `USER_ID_REQUIRED`, `400` `INVALID_USER_ID`, `500` `INTERNAL_ERROR`.

## POST /api/subscription/purchase

Переводит пользователя в Premium. Повторный вызов для того же `userId` снова возвращает `premium` и не создаёт вторую запись.

Заголовки: `X-User-Id`. Тела нет.

`200`

```json
{
  "status": "premium"
}
```

Ошибки: `400` `USER_ID_REQUIRED`, `400` `INVALID_USER_ID`, `500` `INTERNAL_ERROR`.

Способа вернуть Free через API нет.

## POST /api/generations

Создаёт генерацию и сразу возвращает её ID. Картинку этот ответ не содержит.

Заголовки: `X-User-Id`, `Content-Type: application/json`.

```json
{
  "prompt": "A futuristic city at sunset",
  "options": {
    "style": "anime",
    "aspectRatio": "16:9",
    "quality": "hd"
  }
}
```

Допустимые значения:

- `style`: `photorealistic`, `digital-art`, `anime`, `cinematic`
- `aspectRatio`: `1:1`, `2:3`, `16:9`
- `quality`: `standard`, `hd`

Prompt `trigger-error` — обычный допустимый prompt. Он создаёт генерацию, которая позже завершается ошибкой. Сравнение точное: пробелы вокруг не превращают другой текст в этот prompt. Строка из одних пробелов считается пустым prompt.

`201`

```json
{
  "id": "6f1c0c3e-3c2a-4f0a-9d4b-1a2b3c4d5e6f",
  "status": "pending"
}
```

`id` — UUID. Статус в этом ответе всегда `pending`.

`400` `INVALID_REQUEST`, например:

```json
{
  "error": {
    "code": "INVALID_REQUEST",
    "message": "Prompt is required"
  }
}
```

`403`, если пользователь Free передал Premium-опцию:

```json
{
  "error": {
    "code": "PREMIUM_REQUIRED",
    "message": "This option requires a Premium subscription"
  }
}
```

Также возможны `400` для плохого `X-User-Id` и `500` `INTERNAL_ERROR`. При `400` и `403` записи генерации нет.

## GET /api/generations/{id}

Возвращает текущее состояние одной генерации. Клиент вызывает его сразу после создания и далее раз в секунду. Продолжение после таймаута или перезапуска приложения использует тот же путь и сохранённый ID.

Заголовки: `X-User-Id`. Тела нет.

Пока не наступил сохранённый срок готовности, ответ `200`:

```json
{
  "id": "6f1c0c3e-3c2a-4f0a-9d4b-1a2b3c4d5e6f",
  "status": "processing"
}
```

Первый такой запрос переводит хранимый `pending` в `processing`. Повторный запрос до срока снова возвращает `processing`. `pending` в ответе `GET` не появляется.

Первый запрос после срока завершает генерацию и сохраняет конечное состояние. Успешный результат, `200`:

```json
{
  "id": "6f1c0c3e-3c2a-4f0a-9d4b-1a2b3c4d5e6f",
  "status": "completed",
  "imageUrl": "/static/generated/6f1c0c3e-3c2a-4f0a-9d4b-1a2b3c4d5e6f.png"
}
```

`imageUrl` — относительный путь. Клиент разрешает его относительно baseUrl и не использует путь как самостоятельный URL. При переходе в `completed` сервер один раз копирует PNG. Следующие `GET` возвращают тот же `completed` и тот же `imageUrl`: файл заново не копируется, статус не меняется.

Для `trigger-error` первый завершающий запрос тоже возвращает `200`:

```json
{
  "id": "6f1c0c3e-3c2a-4f0a-9d4b-1a2b3c4d5e6f",
  "status": "failed",
  "error": {
    "code": "GENERATION_FAILED",
    "message": "Image generation failed"
  }
}
```

Каждый следующий `GET` возвращает тот же `failed`, тот же `GENERATION_FAILED` и то же сообщение.

Если сервер перезапустился до завершения, первый `GET` после восстановления завершает генерацию по сохранённому сроку. После этого результат тоже стабилен. Отдельного вызова восстановления нет.

Чужой или неизвестный ID даёт `404`:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Generation not found"
  }
}
```

Одинаковый ответ для чужой и отсутствующей генерации не сообщает, существует ли ID. Также возможны `400` для заголовка и `500` `INTERNAL_ERROR`.

## GET /static/generated/{id}.png

Отдаёт байты PNG по относительному `imageUrl`. Клиент запрашивает `baseUrl + imageUrl`.

Заголовки: `X-User-Id`. Тела нет.

`200` с `Content-Type: image/png`.

`404` `NOT_FOUND`, если генерация не принадлежит пользователю или ещё не `completed`. `400` — для плохого заголовка, `500` — для сбоя чтения файла. Повторный успешный `GET` отдаёт тот же файл.

## GET /api/generations

Возвращает серверную историю только этого `userId`. Экран истории клиента этот список не читает и с локальными записями не сливает. Вызов нужен, чтобы история на сервере существовала и была проверяема.

Заголовки: `X-User-Id`. Тела и параметров запроса нет.

`200`

```json
{
  "generations": [
    {
      "id": "6f1c0c3e-3c2a-4f0a-9d4b-1a2b3c4d5e6f",
      "status": "completed",
      "prompt": "A futuristic city at sunset",
      "options": {
        "style": "photorealistic",
        "aspectRatio": "1:1",
        "quality": "standard"
      },
      "imageUrl": "/static/generated/6f1c0c3e-3c2a-4f0a-9d4b-1a2b3c4d5e6f.png",
      "error": null,
      "createdAt": "2026-11-02T08:00:00Z"
    }
  ]
}
```

Порядок — от новых к старым. В списке все статусы пользователя: `processing`, `completed`, `failed`. У незавершённой генерации `imageUrl` и `error` равны `null`. У неуспешной `imageUrl` равен `null`, а `error` содержит тот же `GENERATION_FAILED`, что и `GET` одной генерации. Пустая история — `generations: []`.

`imageUrl` в списке тоже относительный. `createdAt` — время создания в UTC, формат ISO-8601. Ошибки: `400` для заголовка и `500` `INTERNAL_ERROR`.
