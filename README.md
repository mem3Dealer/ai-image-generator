# AI Image Generator

Backend имитирует асинхронную генерацию изображений. Клиент отправляет prompt и параметры, сервер через несколько секунд отдаёт заранее подготовленный PNG. Реальной генерации, внешних API и ключей нет.

## Запуск

Из корня репозитория:

```bash
docker compose up --build
```

Сервер слушает `http://127.0.0.1:8000`.

SQLite и готовые PNG хранятся в `backend/data`. Каталог подключён к контейнеру, поэтому подписка, история и файлы переживают перезапуск.

Каждый запрос передаёт анонимный идентификатор:

```http
X-User-Id: 6f1c0c3e-3c2a-4f0a-9d4b-1a2b3c4d5e6f
```

Это UUID, не авторизация. Первый запрос с новым UUID создаёт пользователя со статусом `free`.

Клиент запускается из `frontend`:

```bash
cd frontend
flutter run
```

Симулятор iOS подключается к `http://127.0.0.1:8000`. Адрес лежит в константе `apiBaseUrl` в `frontend/lib/core/api_client.dart`. Нужен этот IP, а не имя `localhost`: симулятор может разрешить `localhost` в IPv6, тогда как порт Docker слушает IPv4. В `frontend/ios/Runner/Info.plist` для локального HTTP включён `NSAllowsLocalNetworking`. Без этого ключа симулятор может не открыть соединение. Минимальная версия iOS — 15: текущий Xcode не собирает таргет 13.

При запуске подписка на экране может быть Unknown, а история остаётся на устройстве, даже если backend выключен. Как это устроено, написано в разделе «Решения».

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/subscription` | Статус `free` или `premium` |
| POST | `/api/subscription/purchase` | Идемпотентная mock-покупка Premium |
| POST | `/api/generations` | Создать генерацию, ответ `201` и статус `pending` |
| GET | `/api/generations/{id}` | Статус одной генерации |
| GET | `/api/generations` | Серверная история этого пользователя, от новых к старым |
| GET | `/static/generated/{id}.png` | PNG результата, только владельцу завершённой генерации |

Ошибки приходят JSON-объектом `error.code` и `error.message`.

Проверка с чистого пользователя:

```bash
USER_ID="$(uuidgen | tr '[:upper:]' '[:lower:]')"

curl -s -H "X-User-Id: $USER_ID" http://127.0.0.1:8000/api/subscription

curl -s -X POST \
  -H "X-User-Id: $USER_ID" \
  -H "Content-Type: application/json" \
  http://127.0.0.1:8000/api/generations \
  -d '{"prompt":"A futuristic city at sunset","options":{"style":"photorealistic","aspectRatio":"1:1","quality":"standard"}}'
```

В ответе будет `id`. Пока не наступил срок готовности, повторный запрос статуса возвращает `processing`. Примерно через 3 секунды тот же запрос возвращает `completed` и относительный `imageUrl`.

```bash
curl -s -H "X-User-Id: $USER_ID" "http://127.0.0.1:8000/api/generations/<id>"

curl -s -H "X-User-Id: $USER_ID" \
  -o result.png \
  "http://127.0.0.1:8000/static/generated/<id>.png"
```

Стили `anime` и `cinematic`, а также качество `hd` доступны только после Premium:

```bash
curl -s -X POST -H "X-User-Id: $USER_ID" \
  http://127.0.0.1:8000/api/subscription/purchase
```

Повторная покупка снова возвращает `premium` и не создаёт вторую запись. `GET /api/generations` показывает серверную историю этого пользователя.

## Как вызвать ошибку генерации

Prompt должен быть точно `trigger-error`, без лишних пробелов. Запрос проходит обычную проверку и создаёт генерацию. После срока готовности `GET /api/generations/{id}` возвращает HTTP `200`, статус `failed` и код `GENERATION_FAILED`. Следующие запросы возвращают тот же результат. HTTP `500` для этого сценария не используется. Кнопка Retry отправляет тот же prompt ещё раз, поэтому с `trigger-error` генерация снова завершится ошибкой. Чтобы получить картинку, prompt нужно изменить до повтора.

```bash
curl -s -X POST \
  -H "X-User-Id: $USER_ID" \
  -H "Content-Type: application/json" \
  http://127.0.0.1:8000/api/generations \
  -d '{"prompt":"trigger-error","options":{"style":"photorealistic","aspectRatio":"1:1","quality":"standard"}}'
```

## Решения

Free даёт законченный результат: стили Photorealistic и Digital Art, соотношения `1:1`, `2:3` и `16:9`, качество Standard. Premium добавляет стили Anime и Cinematic и качество HD. Это расширение возможностей, а не блокировка базовой картинки. Paywall открывается при выборе Premium-опции, если сервер уже подтвердил Free. Пока статус ещё `unknown`, бесплатная генерация доступна, а Premium-опция сначала вызывает `GET /api/subscription`. Покупка — mock-вызов `POST /api/subscription/purchase`: биллинга нет, повторный вызов оставляет Premium.

Сервер на Python, FastAPI и SQLite в одном контейнере. Так задание поднимается одной командой `docker compose up --build`, без отдельной СУБД, воркера и миграций. SQLite переживает рестарт через каталог `backend/data`. Срок генерации записан в строке как `ready_at`: `POST` возвращает `201` и `pending`, следующие `GET` до срока возвращают `processing`, после срока — конечный статус. Первый завершающий `GET` один раз копирует PNG. Повторные `GET` отдают тот же статус и ту же ссылку.

Форма API — REST и polling раз в секунду. Генерация длится несколько секунд, клиенту нужно показывать ожидание, таймаут и продолжение по сохранённому ID. WebSocket и SSE для одного запроса с опросом ничего не упрощают. `imageUrl` — относительный путь. Клиент собирает адрес как `baseUrl + imageUrl`.

До ответа сервера клиент держит подписку в `unknown` и не подставляет серверный Free нового пользователя. Ошибка сети не затирает уже известный Free или Premium. История на экране локальная: SQLite и файлы картинок. Она открывается после перезапуска приложения и при выключенном сервере. Серверная история в `GET /api/generations` хранится отдельно и на экран не сливается.

Одновременно идёт одна генерация. Её ID записывается сразу после успешного `POST`. Если приложение закрылось во время опроса, при следующем запуске предлагается продолжить ожидание. Опрос сам не стартует. Конечная ошибка очищает активный ID. Retry не нажимается сам: он ещё раз отправляет тот же prompt и те же опции. После `trigger-error` такой повтор снова завершается ошибкой. Чтобы получить картинку, prompt нужно изменить самостоятельно.

На эту работу ушёл один день, 2 ноября 2026, внутри оценки задания 5–8 часов. Отдельного поминутного таймера не было.

## Что сознательно не делается

Эти вещи не входят в текущий объём. Каркас задания без них работает.

- Серверная история не синхронизируется с телефоном. При продолжении экран при онлайн-запуске забирал бы серверный список, скачивал недостающие PNG и складывал их в локальное хранилище.
- На сервере нет отмены генерации. Она была бы отдельным запросом, который переводит ещё не готовую генерацию в конечный статус.
- Очереди из нескольких генераций нет. Для неё понадобились бы список ID и отдельное состояние каждой.
- Нет возврата из Premium в Free, регистрации, пароля, биллинга и внешнего AI. Мок не ходит в интернет.
- Нет случайных сбоев, WebSocket, SSE, отдельного воркера и Postgres. Ошибка генерации вызывается только prompt `trigger-error`.
- Нет соотношений сторон кроме `1:1`, `2:3` и `16:9`.
- Клиент рассчитан на iOS-симулятор и `http://127.0.0.1:8000`. Для физического устройства адрес задавался бы отдельно, вместе с правилом локального HTTP для этого хоста.

## Как использовался AI

Агенту в Cursor были отданы разбор задания, черновики требований, архитектура, API-контракт и реализация по уже согласованным документам. Модель предлагала текст и код. Решения фиксировались после проверки человеком. Ниже ошибки черновиков, которые меняли контракт или поведение экрана.

- Намеренную ошибку генерации модель описала как HTTP `500`. В контракте `trigger-error` завершается ответом `200`, статусом `failed` и кодом `GENERATION_FAILED`. `500` оставлен для неожиданного сбоя сервера. Это проверяет `test_trigger_error_finishes_as_failed`.
- Пустой кэш подписки модель предлагала показывать как Free. Из-за этого Premium-пользователь мог на первом кадре увидеть Free. У клиента появились состояния `unknown`, `free` и `premium`: серверный Free нового пользователя не копируется до ответа.
- Таймаут 15 секунд в первом варианте обрывал генерацию без возврата к ней. ID теперь сохраняется сразу после `POST`. После таймаута и после перезапуска приложения экран предлагает продолжить опрос и не начинает его сам.
- Retry можно было прочитать как автоматический цикл или как исправление ошибки. Кнопка нажимается вручную и снова отправляет тот же prompt и те же опции. С `trigger-error` результат опять `failed`, пока пользователь сам не изменит текст.
- Повторный `GET` после готовности модель не зафиксировала как стабильный. Первый завершающий запрос один раз копирует PNG. Следующие возвращают тот же статус и тот же `imageUrl`. Это проверяет `test_completed_generation_stays_stable`.
- `imageUrl` можно было принять за абсолютный адрес. Клиент собирает запрос из baseUrl и относительного пути.

Требования, архитектура и контракт сверялись с текстом задания до реализации. Серверный контракт затем проверялся `pytest`, клиентский — `flutter test`. Сценарий симулятора эти тесты не заменяют: Paywall, локальный HTTP и история при выключенном сервере смотрятся руками.
